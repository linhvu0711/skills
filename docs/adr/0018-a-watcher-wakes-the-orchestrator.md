# A watcher wakes the orchestrator only when it must act

The Checks of a Run come from a Watcher, a background process that `orchestrate.sh` starts on the user's machine, not from a T3 scheduled task. Each run of a scheduled task is a chat turn in the orchestrator thread, and T3 alerts on every turn end, so the user got an alert every five minutes even when the turn posted nothing. Snoozing the thread does not stop it: T3 alerts on a snoozed thread too. The Watcher runs each Check with no chat turn, writes the board, and sends `/ready-pr` on a conflict itself. It sends the orchestrator thread `/orchestrate check` only when the agent must act: a thread to start, a proposal to make, the Run done, or three failed Checks in a row, and never while that thread is busy. The thread snoozes itself between those turns, so it stays out of the user's list. The cost: the Watcher dies with the machine or its process tree, and `/orchestrate resume` starts it again. A lock on the run folder keeps the Watcher and the agent's commands from writing the state file at once. ADR 0013 and ADR 0015 hold: the thread that gets `/ready-pr` is the same, only the sender moved from the agent to the script.
