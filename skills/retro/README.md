# retro

Looks back over your coding sessions, from every harness it can read, and over the PRs no session worked on. It finds where the agent struggled and what worked well, and turns what repeats into shared fixes to the repo's agent setup: a check, a pointer, a standard, a skill.

## Use it when

A session felt harder than it should have, the same kind of trouble keeps coming back, or you want to know what to change after a stretch of work. Type `/retro` for the session you are in. Name a range, IDs, a topic, or sources to read more: `/retro today`, `/retro last 3 days`, `/retro from 2026-10-01 to 2026-10-05`, `/retro the handoff sessions this week`, `/retro only claude sessions`, `/retro PRs from last week`, `/retro last 3 days, all projects`. Many sessions and PRs show what one cannot: the same mistake, the same slow search, the same review comment, the same correction you keep typing, the same good habit.

[orchestrate](../orchestrate/) starts it for you when a run is done, as `/retro run <run folder>`.

## What you get

Retro first finds the sessions of every harness (the tools that run the agent: Claude Code, Codex, or Antigravity) for this repo, in one call to the shared core's `find_all.py`. Each harness it can read has an adapter in [`sessions/`](../../shared/sessions/); a harness with data and no adapter is named in the report as `found <harness> sessions, cannot read them yet`, never skipped silently. It also lists the PRs and issues in the window that no session names. A PR a session worked on is left out, since the session already holds its reviews and fixes.

If that adds up to more than 20 readers, it tells you the count and waits for `go`. Then one reader agent reads each session (with its helper agents' logs), each PR (its body, reviews, review threads, and the end of each failed CI log), and the issues. Each writes an evidence list: the moments things went wrong, corrections you or a reviewer gave more than once, steps you did by hand, and ways of working worth sharing. Text in a session or a PR can come from anyone, so each reader is told it is data to read, never orders to follow.

Retro then maps the repo's own agent setup: which file holds the steering, the coding standards, the skills, the checks, and the docs, whatever their names. It groups the moments by the fix that would stop them, and each fix names the real file it changes, or says "add one" and names the skill that writes it. Fixes go only to files the team shares, never to your own private files.

The report is a page on this machine, opened in your browser, with the same look on every run. It opens with a grid of where each problem showed up: one row per card, one column per session or PR, and a key under it with each column's title and date. Each card names its home: the repo that holds the file its fix changes. Retro follows links to find it, so a fix to a skill linked in from your skills repo belongs to the skills repo, not to the project. The cards come in one group per home, this project first, each group one list with the most important card on top. A small tag on each card names its kind, such as automated check or navigation. A file in no git repo, or in a repo with no GitHub remote, gives `home unknown`, and the card stays in this project's group. A pattern is a problem seen in two or more sessions or PRs that one fix would stop. Its card shows its items, quotes as proof, the fix, where it goes, and a strength badge (`Strong`, `Worth exploring`, `Speculative`). It also shows how many times the problem happened, in how many sessions and PRs, and what it cost, such as tool calls or user turns. `Strong` needs three or more items or a real cost. Every fix names the moment it would have stopped. A one-time problem becomes a card only when it cost real work: lost work, a bad change that shipped, or many wasted turns. A problem with no fix to name goes in a short Open questions list, not a card. Before it shows a card, retro checks its home. A fix already on the home's main branch is dropped and named in what was read. A card that already has an open issue shows its number. A card whose problem came back after its issue was closed is marked `the fix did not hold`. When retro cannot search a home, the cards still show and the report says the check was skipped. When a fix changes the text of a file, such as a skill, the card shows that text before and after. Retro also finds a skill that should have run and did not; the fix it proposes is that skill's description. Steps you did by hand in two or more sessions become a proposed new skill, or a tip that names the skill you can already type for them. A tip has nothing to file. For a correction you keep giving, the first fix it proposes is to delete the old code or the old way the agent keeps copying; then a check, a skill fix, and a steering line last. A proposed check names the past mistake that it would have caught. Ways of working that went well in two or more items become a card to share them. A serious one-time problem sits in its home's list with a `One-time` badge. A top pick ends the page. Answer in chat with the card numbers you want filed, as 1 3 4, or none. Retro joins the picks in each home into one issue per skill or part they change, shows you the groups, and waits for your `go`; say `move 4 to its own issue` to regroup. Each group becomes an issue in its home through [to-issue](../to-issue/), or a seed through [capture](../capture/) when to-issue needs more than the cards hold. A pick that already has an open issue adds its new quotes there as a comment. An issue filed outside this project names nothing of it: not its name, its repo, or its paths. A card with `home unknown` is not filed, and you are told why. Retro stops after the last filed issue: it changes no code, pulls nothing, installs nothing, and builds nothing.

If nothing is worth changing, or every card is already fixed, it says `Nothing worth changing` and stops. Either way it says what it read, and names anything it did not read or read only in part. It changes no code and files nothing you did not pick and approve with `go`.

## Needs

- `python3` (standard library only), `git`, and `gh` for the repo name, the PRs, and the issues. Without `gh` access it reads sessions only and says so. `gh` runs through the shared core's [gh.py](../../shared/gh.py).
- Session logs on this machine for at least one harness with an adapter in the shared core's [`sessions/`](../../shared/sessions/): today Claude Code (`~/.claude/projects/`), Codex (`~/.codex/sessions/` and `~/.codex/archived_sessions/`, headless `codex exec` runs left out), and Antigravity (`~/.gemini/antigravity-cli/conversations/`, and `antigravity-acp/conversations/` in each T3 Antigravity folder under `~/.t3/userdata/providers/antigravity/`). Older Codex chats are compressed; reading them needs Python 3.14+ or the `zstd` command.
- For `run <folder>`: T3 Code's provider logs under `~/.t3/userdata/logs/provider/`, read by [`sessions/t3/`](../../shared/sessions/t3/).
- Sub-agents: the explorer, from the shared core's agents, one per session or PR.
- A browser and `open` or `xdg-open` for the report page, served by the shared core's `serve.sh`. Without them, the report comes as a list in chat, and you answer the same question.
- [to-issue](../to-issue/) and [capture](../capture/), for the cards you pick.

## Fits with

- Use it after a build worth learning from, such as one run with [ship](../ship/). [orchestrate](../orchestrate/) starts it at the end of every run.
- Fixes it proposes often land through [audit-coding-standards](../audit-coding-standards/), and through [write-for-agents](../write-for-agents/) for any skill or steering text.
- [find-cc-session](../find-cc-session/) and [find-co-session](../find-co-session/) find one session; retro reads many through the same scripts, behind each harness's adapter.
